# Capacity explorer

An interactive page to choose hardware and a model. It has two parts:

- **Usage scenarios** (2026-10-07): ready-made cards (documents for 5 people, vibe-coding a three.js / WebXR app
  for 10, a class of 30, a Computer workshop for 20, long reports for 2, a near-frontier model for 1–2 teachers)
  and **Your own** (a head count, what people do, how they work). Each card lists up to three hardware × model
  pairs that serve that many people with room to spare, what **this farm** can do, and why a popular box falls
  short.
- **The matrix:** for each model × hardware pair at a chosen context per person, how many people at once, how
  fast for one person, the price per person, the first word on a new document, and the longest context.
  Clicking a pair (or a scenario's pick) opens its memory split, its speed as people join (with the measured
  points where they exist) and its people-vs-context curve.

Every figure is labelled **measured**, **calibrated** (a measured model scaled to another box) or **estimated**
(from the specs).

## Where it lives

**The farm serves it** at `http://<box>:41997/lol/capacity`, open like `/lol/self` (no token), and the admin
panel links to it (**Plan capacity ↗**; the Farm app opens it in the system browser). The page reads
`/lol/self` to find this box's GPU in the catalog, marks that column "this farm" and says, in every scenario,
what this box can do. It loads its scripts and data from the farm and nothing else: no fonts, no CDN, so it
works on a farm cut off from the internet.

The shipped files are in `farm/src/capacity/`, the only copy of each:

| File | What it is |
|---|---|
| `index.html` | The page (a system font stack, light and dark). |
| `estimator.js` | The model: KV pages and recurrent state as vLLM 0.30 charges them, a decode step-time fit scaled by memory bandwidth, prefill scaled by compute, two Sparks as copies or tensor-parallel over ConnectX-7. Every assumption is named in `ASSUME` and the page can override the main ones. |
| `scenarios.js` | The scenarios: how each LlmOnLan surface loads a farm (estimator inputs and model needs), the filter, the ranking and the plain-words reasons. Checked by `farm/test/run.js` ("capacity scenarios"). |
| `catalog.json` | 10 hardware entries and 29 models (sizes, attention layout, checkpoints, prices, benchmark scores, community speed reports), with sources and dates. Sources: `catalog-sources.md` here. |
| `measured.json` | `measured.json` from here, trimmed to what the page and the estimator read (31 KB). Generated by `build_page.js`; do not edit. |

Also published as a private Artifact: https://claude.ai/artifact/5voKHTLBktJuUpf9CLk9jt (2026-10-07), from the
single file `build_page.js` writes.

## How the scenarios pick

Each scenario is a way people use LlmOnLan, turned into estimator inputs and model needs (from
`multiuser_implementation_plan.md` §1 and §8, and the spike's profiles):

| Use | Context each | How people work | Reply | Needs |
|---|---|---|---|---|
| Documents in Open WebUI | 32k (whole documents need ≥ 24k each) | out of step | 512 | the OCR model on the same card |
| The coding agent (LOL Vibe's IDE) | 64k | out of step, back-to-back steps | 4,096 | tool calling; an agentic-coding score over its bar (SWE-bench Verified ≥ 60, SWE-bench Pro ≥ 45, Terminal-Bench ≥ 45, or DeepSWE / FrontierSWE ≥ 50) |
| A class chatting | 32k | everyone at once | 256 | reads images (the client lets anyone attach one) |
| The Computer | 32k | out of step | 256 × 4 (thinking) | — ; the box's pick is the model serving the most people |
| Long documents | 128k | out of step | 512 × 4 (thinking) | a BenchLM index of 40 or more |
| The strongest model that fits | 32k | out of step | 256 × 4 (thinking) | all the memory to the model; ranked by quality |

A pair **covers** a head count with room to spare when the middle estimate is 20 % over it and the pessimistic
one still reaches it (a measured cell: the highest level that passed). Pairs that run only on llama.cpp (GGUF)
count for one or two people only: llama.cpp served 2–24× fewer people than vLLM in the spike. Per box, the best
model is the one that covers, good enough (BenchLM index ≥ 40), measured before estimated, then the higher index.
Boxes are ranked by price (cheapest first), except the near-frontier card, ranked by quality. Quality is
BenchLM's open-model index, a third-party aggregate with an opaque method, and the spike's 28-item check where a
model was measured.

## How far to trust it

- **Validated out of sample.** Calibrated on the RTX PRO 6000 alone, the estimator predicted the DGX Spark's
  measured people within the measured range in **17 of 18** cells (mean error 1 %, worst 14 %).
  - Caveat: the GB10 prefill factor and the per-model extra bytes use one Spark measurement each.
- **Two linked Sparks are not measured.**
  - The per-layer exchange delay (55 µs) is fitted to two community reports, and the page lets you change it.
  - Measure the pair once they are cabled, then re-calibrate.
- **Not modelled:**
  - speculative decoding;
  - sparse attention, so long-context figures are pessimistic for GLM-5.3, DeepSeek-V4 and MiniMax-M3;
  - llama.cpp's weaker batching (it served 2–24× fewer people in the spike);
  - people pausing to read.
- **Measured cells were taken with 256-token replies.** A scenario with longer replies keeps the measured head
  count unless memory caps it.
- **Quality** is the vendors' benchmarks, except the spike's own 28-question check for the three measured models.

## Updating

When a new box or model is measured, re-run the spike's harness (`docs/spike/README.md`), then:
1. Rebuild `measured.json` with `build_measured.py`.
2. Re-run `calibrate/`.
3. Copy the new constants into `farm/src/capacity/estimator.js`.
4. Run `node build_page.js`: it refreshes the farm's `measured.json` and the single file.
5. Run the farm tests (`cd farm && node test/run.js`); the scenario test pins a few answers, so a changed answer
   shows up there to check.
6. Commit the farm copies (they ship with the next Farm app), and republish the single file to the same Artifact
   link.
